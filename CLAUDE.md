# CLAUDE.md

MyProfessionalMe: a clickable prototype of a learning & growth platform (growth map, library with avatar-practice learnings, projects & evaluations, profile, counsellor view, admin library and audience-based curriculum mapping). React 19 + Vite + TypeScript, npm. Accounts, roles, each person's learner data, the learning catalogue, curriculum mappings and knowledge bundles live in Supabase (project `myprofessionalme`, ref `njhrxshysipssjyeyivm`, West EU Paris). Production: https://myprofessionalme.vercel.app (Vercel project `myprofessionalme`, deployed with `vercel deploy --prod`).

Source design: Claude Design project `797ed301-7b6d-47eb-9e2d-6d7d2e7483c3`, file `MyProfessionalMe.dc.html`, built on the TaxConnect design system. GitHub: `BartJanCoppens/MyProfessionalMe` (public).

## Commands

- `npm run dev`: dev server
- `npm run build`: `tsc -b` then Vite build (use this as the typecheck)
- `npm run lint`: oxlint
- `supabase db push` / `supabase config push` / `supabase functions deploy manage-users --use-api` / `supabase functions deploy ai --use-api`: apply migrations, auth config and the edge functions to the linked project (no Docker needed). `supabase db advisors --linked` after schema changes.
- `npm test`: Vitest tests (`src/**/*.test.ts`, plus `*.test.tsx` screen tests on jsdom); `npm run test:coverage` adds a v8 coverage report. Tests never reach Supabase (`src/test/setup.ts` swaps in a fake client); `src/test/harness.ts` builds a `Logic` for view-model tests. What each test covers is catalogued in `docs/testing/functional-test-cases.md`. `npm run test:db`: row-level security checks in `supabase/tests/rls.sql` against the linked project, inside a transaction that rolls back; add a case there for every policy change.
- `npm run agents`: regenerate `AGENTS.md` from this file. Run it after every edit to `CLAUDE.md`; never edit `AGENTS.md` by hand.

## Layout

- `src/styles/tokens/*.css`: design-system tokens (colours, type, spacing, motion), copied from the DS. `src/styles/index.css` adds globals and the `pm*` keyframes.
- `src/ds/index.tsx`: TSX port of the DS components the app uses (Button, StatusChip, Tag, Card, Drawer…), inline styles on CSS variables. `Hover` stands in for the prototype's `style-hover` attribute.
- `src/data.ts`: seed data, verbatim from the prototype script; `scripts/seed-content.ts` turns its catalogue, mappings and bundles into the seed SQL of `…_content_tables.sql`. At runtime `useContent()` loads them from Supabase and `setCatalogue()` replaces `LEARN`/`LEARN_BY`/`LEARN_META` in place. `src/lib/contentStore.ts` reads and writes them (`publishMappings`, `saveLearning`, `saveBundleSoon`). `src/types.ts`: tuple and state types.
- `src/model.ts`: `Logic` is a near-verbatim port of the prototype's `DCLogic` class. `renderVals()` derives the whole view-model (`VM`), including the constellation, radar and road geometry. Change behaviour here, not in the screens.
- `Logic.curriculum()` builds the curriculum-mapping view-model; `applyOps()` is the single write path for mappings (drags, signals and copilot proposals all go through it).
- `src/screens/*.tsx`: one file per screen group; each is a transcription of its template block and only reads from `VM`. `Mapping.tsx` is the curriculum-mapping screen.
- `src/App.tsx`: auth gate (sign-in → forced password change → app), then state (one `AppState` object, merged patches like class `setState`), sidebar, header, screen switch.
- `src/lib/supabase.ts` (client, `manageUsers()`, password rule), `src/lib/useAuth.ts` (session, profile, roles → `Access`).
- The **subject** is the person the app shows: `src/lib/useSubject.ts` (who, chosen via "View as"; read-only when not yourself), `src/lib/learnerStore.ts` (their progress, ambitions, interests, avatar prefs), `src/lib/useTeam.ts` (their counsellees). `Logic` takes the subject and writes through `persist()`, which refuses when read-only.
- `src/logic/`: pure, unit-tested derivations (`learner.ts` levels and stage, `team.ts` counsellee summary). `src/screens/SignIn.tsx`, `src/screens/Users.tsx` (User management).
- Podcasts and reels (design v3): `MEDIA` in `src/data.ts` holds each one's player content (host, length, chapters or captions and question); `src/logic/media.ts` the playback and save rules; `Logic.tick()` / `mediaVals()`; `App` runs one 250 ms clock while something plays. A podcast completes itself at 80% listened and a reel on a right answer (owner, Q3): the database allows the owner to set `accepted` for a published learning whose format is Podcast or Reel (`private.is_self_complete`). A podcast or reel without `MEDIA` content shows its cover but no player.
- Knowledge library (admin, design v3): `src/kbVals.ts` builds `vm.kb` (null off-screen), `src/screens/Knowledge.tsx` renders it, `src/logic/okf.ts` holds retrieval (never reads client or licensed sources), OKF v0.2 files, import and the tar download. Bundles are stored per business line (`knowledge_bundles.business_line`, null = firm-wide); edits save shortly after each change. The full design export lives in `Design/` (git-ignored; the design tool's reader stops at 256 KB).
- Create & share (design v3, F12): `src/createVals.ts` builds `vm.create` (null off-screen) and `vm.reviewBadge`; `src/screens/Create.tsx` renders the tabs Mine, Review for peers, New content and, for admins, Review requirements; `src/logic/contribution.ts` holds the pure rules (`ruleMatches`/`mayCreate`, `allowedValues`, `ruleSentence`, strictest `policyFor`, `contentChecks`, `rubricComplete`, `stagesFor`/`stagesOf`, `reviewBadge`); `src/lib/contributionStore.ts` the Supabase calls. `AppState.create` is the signed-in person's own work (`access.userId`, not the subject), loaded by `App` and reloaded after every write. User management has the "Can create for" drawer (creation rules, four-part chip editor `src/screens/RuleChips.tsx`, also used by Review requirements) and, for System Admins, Domain experts.
- Learning record and approvals (F2, F3, v0.7.0): `src/recordVals.ts` builds `vm.rec` (the detail's evidence form or read-only evidence, open feedback, acceptance record, decision box) and `vm.appr` (the "Waiting for you" queue, null off-screen) plus `vm.approvalsBadge`; `src/screens/Approvals.tsx` renders the queue; `src/logic/record.ts` holds the pure rules (`evidenceRule` per format, `evidenceProblem`, `openChanges`, `decisionLine`, `workingDaysSince`, `lastActivityLabel`); `src/lib/recordStore.ts` calls `decide_learning` and `waiting_submissions`. Evidence is text on the progress row (reflection, link, certificate number; files are linked, never uploaded) and goes through `saveProgress` / `save_learning`. `AppState.queue` is the signed-in person's (not the subject's), loaded by `App` and reloaded after every decision and on opening the screen. Decisions are not learner writes: they bypass `persist()` and work in View as; evidence and submit go through `persist()`. My team shows each counsellee's last activity (latest `learner_learnings.updated_at`).
- `supabase/migrations/`: `profiles`, `user_roles`, RLS, private helper functions, first-admin bootstrap. `supabase/functions/manage-users/`: create / remove / reset password / change own password via the auth admin API.
- AI connections (System Admin only): `src/aiVals.ts` builds `vm.ai` (null off-screen and for every other role) plus `showAi`/`navAi`/`goAi`; `src/screens/AiConnections.tsx` renders it; `src/logic/ai.ts` holds providers per kind, `statusOfUse()` (Live / Scripted · why / Waiting for …) and the form checks; `src/lib/aiStore.ts` the Supabase calls; `src/lib/ai.ts` is `complete()`, the one AI path (see Assistants). `supabase/functions/ai/`: `index.ts` (auth, roles, limits, Vault key) over `core.ts` (pure: request caps, provider request, reply parsing, preamble order; tested by `src/lib/aiCore.test.ts`). `scripts/rls-pglite.mjs` stubs Vault (`SHOW=AI` prints those checks).

## Conventions

- Styling is inline style objects using the token values, matching the DS. No Tailwind here.
- `Logic` is rebuilt every render from the current state. After an `await`, use the functional `setState((s) => …)` form because `this.state` is stale (see `send()`).
- The prototype's editable props live in `src/config.ts` and can be overridden from the URL: `?bl=Audit&screen=team&view=radar&marks=off&live=off&motion=off`.
- No seeded persona: progress, levels, stage, ambitions, interests, counsellor and avatar come from the subject. No fictional colleagues or accounts either: Learner's eye shows the viewed person only. `src/logic/noPersona.test.ts` fails if `Lena`, `Mertens`, `Thomas`, `Jonas`, `Peeters`, `Amira` or `Haddad` reappears in the sources. The avatar-practice characters in `AVATARS` are role-play content, not people, and stay. Avatar initials and colour are in `learner_prefs`; an uploaded photo stays in this browser (`localStorage['mpm-avatar:<userId>']`).
- Career stages: Analyst, Consultant, Senior consultant, Manager, Senior manager, Director, Partner. `STAGES` (data.ts) and the `public.career_stage` enum must match; add a stage to both (enum values via a migration) and keep `STAGE_FR` summing to 1. Per-stage grids size from `STAGES.length`. The design still has five stages; do not copy its `STAGES` back.
- Owner's product answers (1 Nov 2026) are in `docs/product/user-journeys-and-epics.md` §7: readiness counts accepted hours only; learners see published learnings only (drafts and "Needs review" are hidden, also from their paths); keep it simple, it is a proof of concept. The functional design for what comes next is `docs/product/functional-design.md`.
- Copy names the subject's counsellor (`Logic.counsellorFirst()` / `counsellorFull()`) and next stage (`nextStage()`); `TARGET` is the firm's next-stage expectation per domain.
- Curriculum mappings live in one `maps` record keyed by audience: business-line keys (`'Consulting'`, …) plus lens-prefixed keys (`'ind:energy'`, `'amb:sust'`, …). `LENSES[i][3]` (canMand) decides whether an audience can carry mandatory items; ambition and profile audiences are always advised. `pending` keys are `audience|learningId`.
- Business lines are Consulting, Audit and Tax & Legal. Audit replaced the design's Advisory on purpose (owner's decision); keep it when pulling new design changes.
- Avatar-practice learnings have format `'Avatar'`; persona, skills and past runs are in `AVATARS` (data.ts).

## Accounts and roles

- **System Admin** (`user_roles.role = 'system_admin'`, no line): everything, and the only role that grants or revokes roles.
- **Domain Admin** (`'domain_admin'` + a business line; a person may hold several): creates, edits, resets and removes users of that line, and edits that line's learnings, curriculum mapping and knowledge bundles. Never manages a System Admin.
- **General Admin** (`'general_admin'`, no line): edits all content: firm-wide and every line's learnings, curriculum mapping for every audience (business lines and the industry, technology, ambition and profile lenses) and all knowledge bundles. Manages no accounts and grants no roles, but opens User management (reading everyone, `profiles`/`user_roles` read policies) to hand out Create & share rights; Domain Admins cannot manage a General Admin.
- Enforcement is in the database (RLS + `private.*` helpers) and in `manage-users`; the UI only hides what the role cannot do. Content follows `private.can_edit_content(line)` (a null line is firm-wide: General and System Admins) and `private.can_edit_audience(audience)`; `Logic.canEditLine()` / `canEditAud()` mirror them in the UI.
- Sign-up is closed; admins create accounts with a temporary password (`must_change_password`), which the user replaces at first sign-in. `[auth.email] enable_signup` must stay `true`: false disables email/password login entirely.
- Never use `user_metadata` for authorization; never put a secret or `service_role` key in the app. `.env.local` holds only the URL and publishable key (see `.env.example`).
- `private.bootstrap_admins` is one-shot: a listed email becomes System Admin only while none exists, and the row is consumed (it is empty now). The database refuses to remove the last System Admin.
- Learner data is per user: `learner_learnings` (state, pct, chosen, `submitted_at`, `evidence_note`/`evidence_link`/`evidence_ref`), `learning_decisions`, `ambitions`, `interests`, `learner_prefs`, plus `profiles.career_stage` and `profiles.counsellor_id`. Read: the formal learning track (`learner_learnings`, `learning_decisions`, `learner_prefs`) by the person, admins who manage them, their counsellor and every General Admin (`private.can_view_track`, Q7/F2-b); `ambitions` and `interests` by the person only (owner's Q8; `Logic.privateData()` hides them in View as). Write: only the person (the update policy is owner-only). A General Admin can View as anyone (`useSubject`).
- Acceptance (F2): the counsellor, a managing Domain Admin, a General or a System Admin decides, never the person (`private.can_accept`), only through `public.decide_learning(user, learning, 'accepted'|'changes', comment)` (security definer): accept, or request changes with a 10–500 character comment, which puts the learning back to in-progress (pct kept) for the learner to resubmit. It writes `learning_decisions` (who, name as it was, when, verdict, comment, evidence snapshot); learners have no write grant there. A podcast or reel completing itself is recorded as `self_completed` by a trigger. The evidence rule per format is `private.evidence_rule` (mirrored by `evidenceRule` in `src/logic/record.ts`; change both): Certification needs a link or certificate number; Book, Website, Mentoring, Coaching, Game, Micro-guide and Case write-up a reflection of at least 140 characters; the rest nothing. Triggers check it whenever the learner submits or edits a submission's evidence, stamp `submitted_at`/`updated_at`, freeze an accepted learning's evidence, and keep accepted items accepted. `public.waiting_submissions()` is the queue: counsellees' submissions plus, for anyone who may accept, those of people without a counsellor. Keep one permissive policy per table and action (merge with OR).
- Nobody but a System Admin may manage a person who is Domain Admin for a line the caller does not administer (`private.can_manage_user` and `manage-users` both enforce it).
- Create & share rights are rules (`creator_rules`): four parts (lines, formats Reel/Podcast/Micro-guide/Case write-up, domains, `ind:`/`tec:` audiences); OR within a part, AND across the filled parts, an empty part = any (any of the three lines; never firm-wide); several rules of a person are OR. "(Consulting OR Tax & Legal) AND Podcast" = `{lines: [Consulting, Tax & Legal], formats: [Podcast]}`. System and General Admins grant anyone any rule; a Domain Admin only to people they manage and only with a filled lines part inside their own lines (`private.can_grant_rule`). A contribution states its line (always one; default the author's), format (its type), domain and an optional audience; some rule must match on insert, update, submit and again at publication (`private.may_create`, `rules_allow`, `rule_matches`), and the four lock after the first submit. `review_policies` use the same four parts plus peers 0..2, expert, quality; every matching one applies and the strictest wins (`private.policy_for`; a contribution without an audience also gets the audience-scoped ones); none = 2 peers, expert, quality & risk; Domain Admins set them only within their lines (`private.can_set_policy`). Status, steps and verdicts change only in `private.submit_contribution` / `review_contribution` / `publish_contribution` (security definer, called through `public.submit_contribution` and `public.review_contribution`); guard triggers check the transition shapes. Peer reviewers come from the author's line or the content's line (`private.peer_candidates(author, line)`), never the author, their counsellor or their counsellees; each person reviews one step. Routing: the domain's expert (`domain_experts`, kept by System Admins) or a System Admin, a General Admin or a System Admin for quality & risk, then peers from the author's line, never the author, their counsellor or people they counsel, and one step per person. Too few people refuses the submit (still a draft). A resubmission runs the whole flow again. Client names are checked in every text field (`CLIENT_WORDS`, mirrored in `private.blocked_term`). The last approval inserts a `learnings` row (`source 'Peer contribution'`, the contribution's line, `created_by` the author); colleagues read that row, not the contribution. Ambitions and interests are never used for routing. No media storage yet: a contribution is text only.
- AI connections and uses are System Admin only, reading included (`ai_connections`, `ai_uses`, RLS on `private.is_system_admin()`). A key goes into Supabase Vault only through `public.ai_set_key()` (System Admin); the table keeps `secret_id` (not granted to clients) and `key_hint` (last 4). Only `public.ai_connection_key()` returns a key, and only to `service_role` (the `ai` function). Deleting a connection deletes its secret. A use takes only a connection whose provider fits its kind (`private.ai_provider_fits`: text = anthropic / openai_compatible, embedding = openai_compatible / other, voice = elevenlabs / other, avatar = heygen / other). `public.ai_live_uses()` (any signed-in user) returns the use keys that are enabled, text, not waiting for a feature, with a connection that has a key and a model; the app and the function both go by it. `ai_usage` (no client access) is counted by `public.ai_count_call()` (service_role) up to `ai_uses.daily_limit` per person per day (UTC); `public.ai_usage_summary()` gives the System Admin calls per use and the top users, never content.
- This project still applies Supabase's default table grants; every new table needs an explicit `revoke all … from anon, authenticated` plus the minimal grants (see `20261030210928_tighten_table_grants.sql`).

## Assistants

Five text uses can be answered by AI: the profile chat ("Talk it through", use `profile_chat`), the curriculum copilot (`curriculum_copilot`), "Read it as …" in the learner's eye (`learners_eye`), the Knowledge library's test retrieval answer (`kb_answer`) and Create & share's "Draft with AI" (`draft_outline`). All go through `Logic.viaAi(use, request, parse)` → `complete()` in `src/lib/ai.ts`, in this order: `window.claude.complete` inside Claude Design; else the `ai` edge function when the use is in `AppState.aiLive` (from `ai_live_uses()`, loaded once by `App` and after every change on the AI connections page); else null, and the caller uses its scripted reply (`Logic.scripted()`, `scriptedCp()`, `scriptedRead()`, the top passages in `kbVals.ts`, the scripted outline in `draftFromPassages`). `?live=off` forces scripted. A failure never falls through to another source.
- Labels never call scripted output AI: `Logic.aiLabel(use)` is "AI assistant" only when AI would answer and the last attempt did, otherwise "Scripted assistant" (or "… · AI did not answer"); reads carry `ai`, the test answer has `kbAnswerNote`, and only an AI outline is saved as `ai_assisted`. A reached daily limit shows as a toast, then the scripted reply.
- The `ai` function: `{ use, system?, messages, max_tokens? }` from any signed-in user (admins-only uses need an admin role) → `{ text }`; `{ action: 'test', connection_id }` for System Admins → `{ ok, model }` or `{ ok: false, error }`. It sends the use's fixed instruction (`ai_uses.preamble`) first and the app's system text after it, caps `max_tokens` (1024; Anthropic gets at least 4096 because thinking counts toward it), messages and size, counts the call before making it, scrubs the key from errors and logs only use, outcome and duration. Providers: Anthropic Messages API (`anthropic-version: 2026-10-21`), or OpenAI-compatible `/chat/completions` at a base URL (OpenAI, Azure OpenAI, EU services such as Mistral). The EU route is the owner's choice of connection, not code: Anthropic's direct API offers global or US processing only. Voice, avatar and embedding uses only store a connection until their feature exists (`waiting_for`). Never put an API key in the client bundle.
