## 4. Server-side AI and real retrieval (prerequisite for steps 3 and 5)

Today retrieval is keyword matching in the browser and every assistant falls back to a scripted reply outside Claude Design.

- [ ] A Supabase edge function proxies the Claude API; the key is a function secret, never in the client. All four assistants (profile chat, curriculum copilot, learner's-eye reading, test retrieval) use it.
- [ ] Ingestion: sources are split into passages per the RAG model (chunk size, overlap), embedded and stored in `pgvector` (`kb_passages`), with sensitivity kept so client and licensed sources are never retrieved.
- [ ] Retrieval in the database: vector similarity, keyword (full-text) and the hybrid weight, threshold and top-k from the RAG model; re-ranking as an option.

## 5. RAG architectures and the logic engine (owner's request, 1 Nov 2026)

### Decisions taken
- The logic engine really runs: **IDP-Z3 now** through a server-side call to a hosted IDP Studio / IDP-Z3 service; **Lean 4** is selectable but labelled "not connected" until a Lean service exists. As in Intelli-Core, nothing the solver did not compute is shown as a solver result.
- The solver's role is chosen **per RAG model**: *Verify* (the answer's claims are checked against the rules; contradictions are flagged), *Infer* (the solver derives the conclusion; passages explain and cite it) or *Both*.
- Where the formal rules live is chosen **per bundle**: one `formal-theory` OKF file, several theory files with each RAG model picking one, or a theory imported from an Intelli-Core workspace.
- A RAG model can switch on any of these architectures, run in parallel and fused into one ranked result (reciprocal rank fusion):
  1. **Vector search**, **hybrid keyword** and **re-ranking** (exist in the configuration).
  2. **OKF graph in parallel**: walks the bundle's concepts, their related links and citations alongside the vector search.
  3. **Knowledge graph**: entity-relation triples extracted across bundles (who, what rule, which threshold), queried by graph traversal.
  4. **Query rewriting**: multi-query and hypothetical-answer (HyDE) expansion; helps vague and NL/FR/EN questions.
  5. **Metadata filters**: topic, sensitivity, source freshness, concept type before ranking.
  6. **Agentic multi-step**: plans sub-questions, retrieves per step, stops when the answer is supported.
  7. **Logic-consistency-driven RAG**: the solver steers retrieval. Missing facts or a failed check trigger further retrieval, and the final answer must be consistent with the theory.

### How a question flows
1. The question is rewritten and filtered (if switched on), then the enabled retrievers run in parallel and their passages are fused.
2. If a logic engine is set: Claude translates the question (and the facts it states) into the solver's formalism (an IDP FO(·) query over the theory's vocabulary, or a Lean proposition). The translation is shown to the user, editable, and stored with the answer.
3. The solver runs the inference task the RAG model asks for (model expansion, propagation or an entailment check in IDP-Z3). Its result, or an unsat core when the facts contradict the rules, comes back with the rules it used.
4. *Verify*: Claude's drafted answer is decomposed into claims and each is checked by the solver. *Infer*: the solver's conclusion is the answer and passages explain it. *Logic-consistency-driven*: missing facts or a contradiction go back to step 1 as new retrieval queries, up to a set number of rounds.
5. The test-retrieval panel shows all of it: retrieved passages per retriever, the translation, the solver's verdict and rules, and the final cited answer.

### Building blocks
- [ ] OKF: a `formal-theory` file type (frontmatter: `language: idp | lean`, `vocabulary`, the concepts each rule formalises; body: the theory) and validation that the theory parses.
- [ ] RAG model settings: retriever switches, fusion, rewrite and filter options, agent step limit, logic engine (none, IDP-Z3, Lean 4), logic role (Verify, Infer, Both), theory selection.
- [ ] Edge function `kb-ask`: orchestration of the steps above; the `idp` call goes to the hosted IDP-Z3 service.
- [ ] Knowledge-graph extraction at ingestion (triples per passage, stored in Postgres).
- [ ] Evaluation set per bundle: questions with expected answers and rules, so RAG models can be compared on the Test retrieval tab.

### Open questions for the owner
1. Where will IDP-Z3 run? It must be reachable from a Supabase edge function, so a hosted IDP Studio or IDP-Z3 web service, not `127.0.0.1`. Intelli-Core's IDP Studio could serve both apps.
2. Which embedding model in production: the design lists Multilingual E5 large, OpenAI text-embedding-3-large and Voyage 3. Hosting E5 ourselves keeps text in the EU; the others are API calls.
3. Intelli-Core import: which export does a bundle take, the `.intellicore` workspace file or an exported theory file, and should a change in Intelli-Core reach the bundle automatically?
4. Knowledge graph scope: per bundle, or one graph across all bundles a creator may use?
