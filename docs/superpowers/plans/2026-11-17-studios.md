# Studios Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the nine studios the v4 design shows next to the Flash card & Exam Studio: Avatar, Reel, Podcast, Game, Slides, Motion, Explainer, Job aid and Case. Reuse code and ideas from GameStudio, Horizon, Socials Reel Studio and Taxatar.

**Architecture:** One studio spine (`src/studioVals.ts` and `src/screens/Studios.tsx` from v4 Task 13) becomes data-driven:
- **Studio definitions.** Each studio is a definition: questions, an item schema, produce options, build steps and a preview kind.
- **What a studio makes.** Its output is a contribution that goes through the existing peer review and publishes into `learnings.content` (one new `kind` per studio).
- **Text.** All text AI goes through `complete()` and the `ai` edge function.
- **Media services.** Each sits behind its own edge function adapter, keyed through the existing AI connections (Vault, providers `elevenlabs` and `heygen`, use kinds `voice` and `avatar`).
- **Media files.** They go to one private Supabase Storage bucket.

**Tech Stack:** React 19, Vite, TypeScript, Supabase (Postgres, RLS, Storage, edge functions), Vitest, PGlite RLS runner.

**Spec:**
- The v4 design's `STUDIOS` block. Use its questions, items, rows and build steps per studio; names in examples become roles.
- The owner's answers of 17 Nov 2026:
  - Build the other studios, taking code and inspiration from the four projects (this reverses D1).
  - Voices: ElevenLabs with a browser-voice fallback, from an admin-approved list of stock voices.
  - Video: rendered in the browser.
  - Avatar practice: a live video avatar.
  - Order: cheapest first, one release per phase.

## Review Focus

1. **AI-generated SVG or game code carrying script or external loads.** Sanitised (SVG) or refused by the static scan, and sealed by CSP (games). Tests in Phases 2 and 4.
2. **A voice or avatar service is not configured or fails mid-way.** The studio says so and offers the fallback; nothing pretends to be the service. Tests in Phases 3 and 6.
3. **A creator tries to use a non-stock voice or look** (a crafted API call with a voice id outside the list). Refused by the edge function. Case in Phase 3.
4. **A long media job and the tab is closed.** The draft keeps its last good state, and the job is marked failed or resumable; no half file is published. Tests in Phases 3 and 5.
5. **A play-test or practice run.** Never written as progress or score (`test` flag). Cases in Phases 4 and 6.
6. **An untrusted `.horizon` file.** Any upload is refused before storage, with a reason, when:
   - it is over 50 MB, or not JSON;
   - it does not say `format: 'horizon'`;
   - its `version` is newer than the player supports.

   In the player:
   - Every SVG goes through `sanitizeSvg()` + `instance()`.
   - Calc `animation.code` is never executed (poster only).
   - Images and media must be `data:` URLs; any other URL is dropped.
   - Nothing calls Horizon's `/api/*` or any outside address (CSP for the player frame).

   Tests in Phase 3.

## Phase 4 tasks (written at the start of Phase 4, 18 Nov 2026)

**Decisions settled here** (from S6, S7, S11, the reuse map and the owner reuse rule; recorded in `decisions.md` at 4.6):
- **What a game is.** A Game is studio rows plus one built item. The rows are one `Concept` (text: the set-up; text 2: the win condition), at most one `AI role` (text: who the AI plays; text 2: what it knows and hides) and `Round N` rows (text: what the player sees; text 2: the answer). After them comes one game item `{kind: 'game', files: {'index.html', 'game.js'}, for: {role}, review: {passed, reasons} | null, made: 'ai'}`. `ITEM_MAX.Game` stays 10, so there are at most 9 rows.
- **Content from the rows, not from AI.** The game reads its content through `getData()`, which comes from the rows at publish time. Peer reviewers review exactly what plays, and editing a round needs no rebuild. GameStudio's AI "data" step is not ported. The build step "Writing the game content" turns the rows into the data, without AI.
- **Two files only.** `index.html` holds the markup and one inline `<style>`; `game.js` holds the logic. GameStudio's `style.css` is dropped. Caps: index.html ≤ 16,000 characters and game.js ≤ 32,000. They are sized so that a logic call that continues a file stays under the `ai` function's 60,000-character input cap: system + concept + index.html + the part written so far.
- **The hidden knowledge stays in the contribution.** The `AI role` row's text 2 stays in `contributions.items`, which learners cannot read (`contributions: read`: author, reviewers, System Admins). `learnings.content` carries `role: {kind, about}` without it. The `ai` function reads it with the service role through `contributions.learning_id`. GameStudio's `game_secrets` table is not ported, so the knowledge is never copied.
- **House rules.** The house rules are the `studio_game` use's instruction (`ai_uses.preamble`), which a System Admin edits on the AI connections page. GameStudio's `ai_settings`/`houseRules.ts` are not ported. The AI house-rules review is a build step on `complete()`. Its verdict is stored in the game item, so it is client-reported (logged as a PoC shortcut). The enforced gates are the static scan in SQL (check and submit), the frame's sandbox and CSP, and human peer review.
- **Completion stays as it is.** Game is a reflection format (`REFLECTION_FORMATS`, `private.evidence_rule`) and goes to the counsellor (functional design F2-a; `docs/product/functional-design.md` lines 160, 175, 218). Studio-made Games keep that rule. Playing or finishing a run never writes `learner_progress`. `record.sync.test.ts` stays unchanged.
- **Runs.** A run is on a published learning (`test = false`) or on a contribution (`test = true`: a play-test by its author or one of its reviewers). Leaderboards read finished non-test runs only, through one definer function (S11).
- **"My team only"** means the people who share your counsellor, that counsellor, and your own counsellees (`profiles.counsellor_id`). Listed as an owner question.
- **Port target.** Copied code goes to `src/game/` (player and bridge, like `src/horizon/`) and to `src/logic/` (pure rules). Nothing is imported from `/Users/comendacoppens/GameStudio` (S7).

A learner can therefore not forge the character's earlier lines, and the score is bound to what was said.

# Phase 7: Trajectory AI (release v0.16.0)

**Owner request, 18 Nov 2026; built after all studios. Detailed plan written when Phase 6 ships.** An admin builds a trajectory (for example an ITAA accreditation) together with an AI that proposes the structure and drafts the material. The AI proposes; the admin decides.

Owner answers: sources are the Knowledge library bundles, existing learnings and documents the admin uploads (for example the ITAA syllabus), always cited, no web. AI-made material goes through the normal studio and review flow and is marked "Made with AI".

Scope:
- **Where:** a "Build with AI" panel beside the trajectory editor, with a chat and a structured plan that the chat edits. Admins who can edit the trajectory only.
- **1 · Brief.** The AI asks, then summarises: goal and credential, audience (stage, business line), starting level, time budget and deadline, issuing body rules, constraints. The admin can upload the body's syllabus or regulations (PDF, into the `media` bucket) as sources.
- **2 · Proposed plan.** Modules in order of difficulty and depth (foundation, applied, expert), each with learning goals, estimated hours, the proposed format(s) and why, the sources it rests on (cited), and the check points (evidence, counsellor sign-off, exam). Existing learnings from the library are proposed first; only gaps are marked "to create".
- **3 · Curate.** Each module is a card: accept, edit, reorder, remove, or "ask the AI about this module". Chat revises the plan ("shorter", "more VAT cases", "add a mock exam"). Nothing changes the trajectory until "Apply".
- **4 · Apply.** Accepted modules become trajectory steps: existing learnings link directly; "to create" modules become placeholder steps that show "being made".
- **5 · Create material.** Per placeholder, or several at once: "Draft with AI" opens the matching studio (Flash cards, Exam, Case, Job aid, Explainer, Motion, Slides, Podcast, Game, Reel, Avatar) with the brief, goals, depth and cited sources filled in, and runs its existing AI draft step. Each draft is a contribution in the admin's name and goes through the usual check, review and publish; once published, the placeholder step links to it.
- **Reuse:** the one AI path (`complete()`, a new AI use `trajectory_ai`, metered, off by default), the studio drafting path and `marked()` data blocks, the Knowledge bundles, `media` storage, the trajectory editor and store.
- **Data:** the plan and the conversation are kept with the trajectory (a `trajectory_plans` row: messages, plan JSON, sources), so the admin can come back.
- **Honest UI:** the AI never invents a source; a module without a cited source says "No source yet". Hours and difficulty are proposals the admin confirms.

## Phase 7 tasks (written at the start of Phase 7, 18 Nov 2026)

**Decisions settled here** (from the Phase 7 scope, the owner's answers of 18 Nov 2026, the owner reuse rule and the Phase 1 to 6 rulings; recorded in `decisions.md` at 7.6):
- **One text path, no new function.** Trajectory AI is one new text use, `trajectory_ai`, on the generic `ai` path through `complete()` (`L.viaAi`): `admins_only`, kind text, off by default, no scripted fallback (`NO_SCRIPT`). It is not server-only: nothing in the request is hidden from the admin who sends it. The AI proposes and the admin decides, so no verdict needs to be server-owned. The `ai` function's existing admin check (any admin role) is the gate. A Domain Admin could spend calls on another line's topic, but every call is metered and can write nothing (accepted, recorded).
- **Who.** Every trajectory editor: the panel is offered where `refusal(L, t)` is null (the mirror of `private.can_write_trajectory`), never in View as. The plan and source rows use the same rule in RLS through `private.can_plan_trajectory(p_id)`. A Domain Admin therefore cannot plan, upload to or apply to another line's trajectory, nor to a live trajectory with a mandatory map (D2).
- **Sources: three kinds, always cited, no web.**
  - **Knowledge library passages:** the bundles the admin picks, from `usableBundles(bundles, t.business_line)` (the creators' rule, so a cited bundle can later ground the studio draft). Client and licensed passages are never read (`usablePassage`).
  - **Published learnings:** the trajectory's line and firm-wide, as a catalogue the AI may propose ("existing") and cite.
  - **Uploaded documents:** PDF only. The text is extracted in the admin's browser with `pdfjs-dist` (Mozilla, lazy-loaded, pinned exactly, at least 4.2.67, the CVE-2024-4367 fix; `isEvalSupported: false`, `disableFontFace: true`). It is cut into passages tagged with their page and stored in a row; the original PDF goes to the `media` bucket so a citation can be opened. No new service and no server-side extraction. A scanned PDF without a text layer is refused ("no OCR").
- **Never the whole document.** Each call sends a bounded pool: the passages the current plan cites first, then the best keyword matches (`rankPassages`, factored out of `okf.retrieve`), at most 24 passages of 700 characters, 40 catalogue rows and the last 12 messages. The whole request stays under 50,000 characters (`LIMITS.chars` is 60,000). Cost is bounded per call and metered per day (calls and characters, `ai_count_call`).
- **Citations are pointers the app checks.** In each request the passages are numbered `P1…Pn` and learnings are cited by id (`L12`). The reply may cite only those. Any other citation is dropped and counted, and the panel says so. A module left without a source shows "No source yet". A citation is stored with its label and a 160-character quote, so it still reads after a bundle changes. The app checks that a citation was given in the request, not that the passage says what the module claims (shortcut, recorded).
- **The plan is a proposal; only Apply writes.** Modules come in as not accepted. The admin accepts, edits, reorders or removes each one. A revision keeps a module accepted only when the AI left it unchanged. "Apply" writes the accepted modules as steps through the editor's one write path (`patch` → `saveTrajectorySoon`), and only steps: name, credential, months and maps stay the admin's to set.
- **Apply is idempotent.** Every applied step carries `from: 'p:<module id>'`. A module that already has a step from it is skipped. Two more skips: a learning already used in the trajectory, and a step whose title is already there. These catch a module re-proposed after "Start over". Apply never removes or changes a step.
- **Check points.** A module's check points are `evidence` and `signoff` only. Accepting any `exam` step awards the credential (`decide_trajectory`), so the exam is one plan-level `finalExam`, added only when the trajectory has no exam yet. A mock exam is a Practice exam learning made in the Flash card & Exam Studio.
- **What Apply makes:**
  - existing material → a `learn` step;
  - a studio format → a placeholder step, the new kind `make`;
  - a manual format (External course, Classroom, Book, Mentoring) → an `evidence` step titled "<format> · <module title>", which the learner proves with a link or note and the counsellor signs off;
  - `signoff` → a `check` step after the module's material; `evidence` → an `evidence` step.
  - Windows spread over the trajectory's months: module i of n gets `win = ceil((i + 1) * months / n)`, and the final exam gets `months`.
- **The placeholder step.** It is `{id, k: 'make', title, fmt, hours, win, req, pre, from, cid?}`, where `fmt` is a studio format and `cid` the contribution drafted for it.
  - **Learners** see "Being made · <format>" with no action. It is never required and never blocks progress or completion, whatever `req` says.
  - **Linking.** When the contribution with that `cid` is published, the database turns the step into `{k: 'learn', lid: <learning id>}`, keeping its id, `win`, `req`, `pre` and `from`, so enrolment state stays keyed. Two triggers do it: `after update of learning_id` on `contributions` touches the trajectories that hold the `cid`, and `before insert or update` on `trajectories` (`private.link_made_steps`) converts. A stale debounced save from an open editor that sends the old `make` step is converted again, so no client write can undo the link. Its `req` then applies: the editor warns first.
- **Drafts are the admin's own contributions.**
  - "Draft with AI" builds the draft from the module (`briefDraft`). One placeholder opens the matching studio at its Draft step and runs that studio's existing draft step. Several are drafted one after another and saved as drafts the admin finishes later.
  - Only studio formats get "Draft with AI"; manual steps never do.
  - The admin's creation rules apply as for any creator (no bypass; owner question 1).
  - The studio's draft step reads the module's goals, depth and cited passages through one new optional `NewDraft.brief`.
  - Check, peer review and publish are unchanged, and "Made with AI" comes from the existing `made`/`ai_made` path.
- **Data.**
  - `trajectory_plans`: one row per trajectory (pk `trajectory_id`) holding the plan JSON, the messages and the picked bundle ids. It has no client delete: "Start over" clears it.
  - `trajectory_plan_sources`: the uploaded documents, at most 10 per trajectory.
  - Both cascade with the trajectory.
  - A source file lives at `<added_by>/<source id>/<file>.pdf`: the existing two-uuid path shape (`private.media_path_ok` unchanged), with a second branch in `can_write_media`/`can_read_media` for a plan source.
  - Deleting a trajectory removes its source files first (`deleteTrajectory`).
- **Prompt injection.** Every passage, catalogue row, brief field, module text and admin message goes in `marked()`. The answer is strict JSON. The reply is shown as plain text (React text, no HTML or markdown rendering). Formats, learning ids and citations are checked against what was sent. Nothing applies itself. An uploaded document is scanned at upload: a blocked client term refuses it (`blockedTerm`, the client-words rule), and text that reads like instructions to an AI is flagged on the source (`injectionFlags`, from `_shared/avatarGuard.ts`) but kept as data.
